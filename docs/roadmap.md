# 后续技术设想 / Roadmap（2026-11-04）

> 来源：用户 2026-11-04 口述的三个后续方向。本文只做**设想与工程拆解**，不是已交付能力；
> 以下均为后续工作 / 技术设想，不代表当前已完成。
> 术语说明：「双全工」按用户口述拆字理解为 **双工 + 全工具** 的实时语音模型/架构
> （既能像打电话一样同时听/说，又能在对话中直接调用全部工具）；如原意不同可再改。

---

## 0. 三条设想的共同目标

现在的系统是「用户说话 → 数字人执行」。下一阶段要让数字人从**被动执行者**变成：

1. **能看世界并主动提议改造世界**（VLM 观察地图 → 提出改动 → 外部 Agent 工程化 → 地图工具链生成 → 热插拔）；
2. **能像打电话一样自然交流**（全双工、可打断、可同时听说、对话中直接调工具 → 双全工实时语音）；
3. **能自己扩展自己的能力**（提出需求 → 外部 Agent 生成/编译脚本或插件 → 注入运行中的游戏）。

三条线最终汇成一个形态：**数字人 + 外挂 Agent + 可实时演化的世界与能力**。

## 1. 技术点 A：VLM 看地图 → 外部 Agent → 地图工具链生成/热插拔

### 1.1 目标链路

```
数字人在游戏内运行
  → EyeCamera / 自由观察相机 实时画面
  → VLM 理解地图构成（区域/建筑/道路/障碍/地标/可达性）
  → 数字人形成"意图"：例如"这里太空了，给我加一条商业街/一个公交站/一排树"
  → 生成【模糊指令】交给外部 Agent（本地/远程，带游戏状态与地图 DSL）
  → 外部 Agent 细化成【工程方案】：
       区域、模块类型、占地、朝向、风格、连接关系、预算、约束
  → 调用地图设计工具链：
       Blender 程序化模块生成 → GLB / 场景清单 / 统计
       → 集成数据（碰撞 AABB / 导航图 / 锚点 / 地面高度）
       → Unity 资产与场景增量更新
  → 热插拔进正在运行的游戏（地图 chunk / 资产包 / 场景增量）
  → VLM 再看一遍，验证"改成了没有、好不好看、是否可达"
  → 不满意 → 反馈给 Agent 迭代
```

### 1.2 现有基础（已具备，可直接复用）

| 能力 | 现有实现 |
|---|---|
| 程序化地图生成 | `Maps/SovietBlueHour/tools/`：`plan.json` + 30+ 模块类型生成器（住宅/公共/工业/地标/雕塑/公交站…）+ `kit.py/sitekit.py/look.py`；48 街区、38k 对象、142 万面，构建 1247s |
| 导出/导入 | GLB 导出 → Unity UniGLTF（ReverseZ、URP）→ 51 网格 prefab；坐标契约已实测 |
| 集成数据 | `integration/make_unity_data.py`（碰撞 91 AABB、导航 3486 节点/8551 边、46 锚点）、`make_ground_height.py`（401×305 1m 高度图） |
| 场景装配 | `SovietBlueHourSceneBuilder.cs` 一键复制旧场景 + 换环境 + 接相机/灯光/后处理 + 写 Build Settings |
| 运行时世界 | `MapWorldProfile` + `WorldData` 大地图模式（碰撞/导航 A*/锚点/区域查询/地面高度） |
| 视觉理解 | `VisionObserver` + `QwenVisionClient`（EyeCamera/摄像头、四方向观察、视频记忆、多模型回退） |
| 外部 Agent | Unity MCP（编辑器内查询/执行/Play/截图）+ 可外挂的本地/远程 Agent 进程 |
| 数字人自主性 | 现有 `Brain`/`Director` 主动行为、任务运行时（Lua）已能调 Unity 工具 |

### 1.3 需要补的关键工程件

1. **地图 DSL / 工程化中间表示（Map Intent → Map Plan）**
   - 输入：模糊自然语言 + VLM 观察 + 当前地图版本；
   - 输出：结构化 `MapPlan`：
     ```json
     {
       "region": {"center": [x,z], "radius": 40, "constraints": ["keep_road"]},
       "modules": [
         {"type":"shop_row","footprint":[12,6],"facing":"+z","style":"soviet_80s","count":3},
         {"type":"bus_stop","anchor":"existing_road_42","offset":[6,0]}
       ],
       "connectivity": {"must_connect":["central_plaza","metro"], "max_walk_m":120},
       "budget": {"max_tris":300000, "max_build_seconds":600},
       "acceptance": ["no_overlap","reachable","nav_graph_connected","looks_like_soviet"]
     }
     ```
   - Agent 在 DSL 上规划/校验，Blender 工具链只吃 DSL 参数（不直接吃自然语言）。

2. **视觉定位（VLM 语义 → 游戏坐标）**
   - 方案：EyeCamera 位姿 + 射线/深度 + 场景语义层（建筑/道路 ID 标注）+ 俯视小地图联合定位；
   - VLM 只输出「相对画面/区域的语义描述」，坐标由确定性层投影，避免模型瞎猜坐标；
   - 可加一层「区域网格 ID」：把小地图切成 grid，VLM 指认 grid + 地标，精度不够再追问。

3. **增量构建（避免每次 1247s 全量重建）**
   - 按街区/地块分 chunk：只重建受影响 chunk 的 GLB、碰撞、导航、地面高度；
   - `plan.json` 作为单一事实源，生成器支持 `--patch region.json` 只产出 delta；
   - 增量集成数据：导航图局部重连 + A* 可达性重验；碰撞/地面高度局部重烘；
   - 场景装配从「全量复制」升级为「资产引用替换 + chunk 挂载」。

4. **运行时热插拔**
   - 短期：**资产包/Addressables** 方式（地图 chunk 预制体 + 数据 JSON），运行时卸载/挂载；碰撞与导航数据热替换；
   - 中期：runtime GLB 导入（UniGLTF runtime）或预生成 AssetBundle，避免编辑器依赖；
   - 长期：地图 chunk streaming + LOD + 物理/导航 tile 流式加载，支持"边玩边改"。

5. **一致性与回滚**
   - 单一事实源（plan.json + scene manifest + 数据版本号）；
   - 每次生成产出 `map_pack_vN`（GLB + 碰撞/导航/锚点/高度 + 元数据），可回滚；
   - 自动验收：碰撞重叠、出生点可达、关键锚点连通、地面高度连续、三角面/材质预算、QA 截图。

6. **数字人闭环**
   - 数字人提议 → 用户确认（可选）→ Agent 生成 → 自动 QA → 热插拔 → VLM 复看 → 满意/再改；
   - 把"改地图"也接入现有 Action Lane（`game.request_map_change(...)` 工具 + 契约 + 回执），
     保证可审计、可拒绝、可回滚。

### 1.4 里程碑

- **A1**：地图 DSL + Agent 生成 `MapPlan`（离线跑通，人工确认）；
- **A2**：增量 chunk 生成 + 数据重烘 + 资产包热挂载（先支持静态装饰/小地块）；
- **A3**：VLM 观察 → 提议 → Agent → 自动生成 → 热插拔 → VLM 复看闭环；
- **A4**：运行时 GLB/资产流式加载，支持更大范围改造。

## 2. 技术点 B：「双全工」实时语音（全双工 + 全工具）

> 目标：像打电话——不用等我说完、可以抢话、可以边说边听、对方能边聊边"动手"（调工具/执行任务）。

### 2.1 现状（已实现的部分）

- 流式 LLM（SSE）+ 分句流式 TTS（MiniMax PCM，首块 0.3–0.5s）；
- sidecar 全双工采集/播放：AEC（pyaec）+ VAD（Silero）+ ASR（SenseVoice）；
- **可打断**：AI 说话时用户开口 → barge_in → 停播 + 取消当前对话轮；行动车道不被误杀；
- 口型：UDP 每 20ms 五元音权重 → blendshape；
- 但整体仍是**轮次式**：一次用户说完 → ASR final → LLM → TTS 队列，模型层没有"同时听说"。

### 2.2 目标能力

1. **真全双工**：持续听 + 持续说；可同时进行（不依赖"说完再答"）；
2. **自然轮次**：用户停顿/语气词/抢话/背景音都能处理；支持 backchannel（"嗯/对"）；
3. **对话中调工具**：说到"帮我走过去/看看那边/把地图改一下"时，语音模型直接发起工具调用，动作与语音并行；
4. **低延迟**：首字 < 500ms，打断响应 < 300ms；
5. **可打断语义**：打断"说话"≠打断"行动"（现有双车道规则延续）；
6. **情绪/韵律**：TTS 情绪随对话状态变化（现有表情/神态映射可复用）。

### 2.3 架构选项

**方案 A：端到端实时语音大模型（Speech-to-Speech / Omni Realtime）**
- 输入音频流 → 模型原生输出音频流，延迟最低、轮次最自然；
- 代价：可控性/工具调用/中文人设一致性弱，且需把 Unity 状态/工具注入；更多依赖云端实时接口。

**方案 B：级联全双工（现有链路升级）**
- 持续 ASR（流式 partial）+ VAD/轮次检测 + LLM 流式 + 流式 TTS；
- AEC 双工、可打断、可并行；工具调用走现有 Action Lane；
- 优点：完全复用现有双车道/契约/回执体系；缺点：端到端延迟叠加，轮次仍靠 VAD 判断。

**方案 C：混合（推荐路线）**
- 前端：**双工音频层**（AEC/VAD/流式 ASR + 流式 TTS + 打断）保证电话感；
- 中端：**双车道 LLM**（Talker 车道即时说话；Action 车道接工具/任务；两者共享对话状态）；
- 后端：工具调用结果以事件形式注入 Talker（"正在走/到了/没走到"），保持事实一致；
- 未来可把 Talker 换成原生 Omni Realtime 模型，外层协议不变。

### 2.4 关键工程点

1. **AEC/回声**：sidecar 已有 pyaec + 参考信号；双工下要保证"自己说话时仍能听到用户"；
2. **轮次检测**：VAD + 语义端点（停顿/语气词/句法）+ 可配置"等待窗口"；
3. **打断语义**：区分"打断说话"（取消 TTS/当前轮）与"打断行动"（取消任务）——沿用现有 `CancelDialogueTurn` vs `Missions.Cancel` 分离；
4. **工具调用与语音并行**：Talker 发起 `tool_call` → Action Lane 执行 → 回执事件回流 → Talker 继续播报；避免"说完才动"；
5. **延迟预算**：ASR partial 200ms、LLM 首 token 300–500ms、TTS 首块 300–500ms、总首字 < 1s；
6. **状态机**：Listening / Thinking / Speaking / Acting 四态并发（不是互斥），需要资源仲裁（voice/body/camera）；
7. **音频-视觉同步**：口型、表情、动作与语音事件对齐；打断时要清理队列；
8. **成本/稳定性**：流式并发限流、重试、降级（回退到轮次式）。

### 2.5 里程碑

- **B1**：现状优化——更低延迟、双工打断更稳、partial ASR 可视化；
- **B2**：Talker/Action 并行——说话中直接触发工具（"边走边说"到"边说边做任何事"）；
- **B3**：接入实时语音模型（Omni Realtime）或自建双工管线，达到"打电话"体验；
- **B4**：情绪/韵律/人格一致性 + 多语言。

## 3. 技术点 C：终极形态——数字人自主提出需求，外部 Agent 生成地图/脚本并注入游戏

### 3.1 目标

- 数字人不再只是"在固定游戏里行动"，而是能**扩展游戏内容与自身能力**：
  1. 提出需求（"我想在这里办个夜市/我想能飞/我想有个新技能/这段剧情改成…"）；
  2. 外部 Agent 把模糊需求细化成工程方案；
  3. 生成资产/脚本/插件；
  4. 编译/校验后**注入正在运行的游戏**（像外挂插件/热更新）；
  5. 失败可回滚，成功可持久化。

### 3.2 两个注入层级

| 层级 | 产物 | 注入方式 | 风险/难度 |
|---|---|---|---|
| 数据/资产级 | 地图 chunk、prefab 变体、配置、Lua 任务脚本 | AssetBundle/Addressables 热挂载；Lua VM 热替换 | 中低（现有 Lua/资产管线可扩展） |
| 代码级 | C# 脚本/插件、新工具、新动画/材质 | 编译成程序集 → 运行时加载（AssemblyLoadContext / Mono.Cecil / 热重载框架） | 高（Unity 运行时限制、安全、版本） |

### 3.3 目标流水线

```
数字人意图（自然语言 + 世界状态）
  → 外挂 Agent（规划 + 编码 + 自测）
  → 产物：map_pack / lua_script / csharp_plugin / config
  → 沙箱校验：契约、权限、预算、静态检查、单测/回放
  → 编译：Lua 字节码 / Roslyn 编译程序集 / 资产打包
  → 热注入：Lua VM 替换、AssetBundle 挂载、程序集加载（受控）
  → 运行时验证：验收脚本 + VLM 复看 + 回执
  → 成功：写入 mod 清单/版本；失败：回滚
```

### 3.4 现有基础与缺口

**已有**
- Lua 任务运行时（MoonSharp，沙箱内无 io/os/CLR）、Tool Registry、契约/预算/回执；
- 外部 Agent（Unity MCP 可在编辑器里执行代码/操作场景）；
- 地图工具链（可生成资产与数据）；
- 事件总线/事实播报/双车道（保证"改动"与"说话"一致）。

**缺口**
- 运行时 C# 热加载（Unity 的域重载/程序集加载限制）；
- 运行时地图/资产增量导入与物理/导航重建；
- 插件安全（权限、资源、崩溃隔离、回滚）；
- 插件版本/依赖/兼容性管理（mod manifest、semver、冲突检测）；
- 在线验收与可观测性（性能/内存/帧率预算）；
- 用户授权与内容审核（数字人自主改世界的边界）。

### 3.5 里程碑

- **C1**：Lua 级"能力插件"——数字人提议 → Agent 生成 Lua 任务/技能脚本 → 热替换执行（先做行为，不动 C#）；
- **C2**：地图/资产级插件——地图 chunk/装饰包生成 → 资产包热挂载 → 导航/碰撞增量重建；
- **C3**：代码级插件——受控 C# 编译 + 程序集热加载 + 崩溃隔离/回滚（可先从"重启级"更新开始）；
- **C4**：完整闭环——数字人自主提出 → Agent 生成 → 注入 → 验证 → 持久化，形成"可演化的世界"。

## 5. 风险与边界（写设想时要诚实标注）

1. **安全**：数字人/Agent 自主改世界必须沙箱 + 权限 + 用户确认 + 可回滚；不能让模型直接写 C# 进运行时。
2. **一致性**：地图几何/碰撞/导航/锚点/地面高度必须同版本原子更新，否则会出现穿墙/浮空/不可达。
3. **性能**：增量构建与流式加载要控制三角面/材质/内存/帧率预算；全量重建 1247s 不能用于在线闭环。
4. **延迟/成本**：VLM 观察 + Agent 规划 + 生成 + 编译 + 验收是分钟级，不能假装实时；需要异步任务 + 进度播报。
5. **确定性**：程序化生成要固定 seed，保证可复现/可回滚；验收脚本要覆盖新旧地图。
6. **版权/内容**：生成资产与脚本的授权、审核、来源记录。
7. **研究性质**：A/B/C 均为后续设想，当前版本只交付了「固定地图 + 双车道任务/对话 + 语音/视觉」的基础能力。
